# Web research: what can add value to the brief

Reviewed November 6, 2026. This is a reading of public documentation, papers
and vendor posts against what the project is trying to do; nothing here was
installed, run or benchmarked, and every number is its author's. It extends
the [related-project findings](research.md) of November 4 and follows the
[host context cost analysis](host-context-cost-2026-11-06.md) and the
[controlling-context candidate](controlling-context-2026-11-06.md) of today.

What the project is trying to do, in one paragraph: a deterministic,
read-only collector selects exact source excerpts for a request; an optional
small local model drafts the prompt the cloud assistant (Claude or ChatGPT)
reads; the user pastes the brief. The retained measurements say the cost the
brief must displace is the number of tool turns the host takes before its first
supported answer, and the broad log or directory reads it makes along the way.
The brief itself is 400 to 1,300 tokens. So the question for each source below
is: does it reduce host turns, prevent broad reads, or make the brief more
trustworthy, within this project's bounds (no runtime dependencies, no cloud
client, exact evidence unchanged, model output unverified)?

## Findings and candidates

### 1. Vendor guidance on context: just-in-time retrieval with lightweight identifiers

Anthropic's September 2025 engineering post describes agents keeping
"lightweight identifiers (file paths, stored queries, web links, etc.)" and
loading data at runtime, with folder hierarchy, naming, sizes and timestamps as
relevance signals, head and tail reads for large data, and the goal of the
smallest set of high-signal tokens. It also describes compaction and
note-taking for long sessions, and sub-agents that return 1,000 to 2,000 token
summaries. The Agent Skills post (October 2025) names progressive disclosure as
its central principle: metadata first, the full instructions once relevant,
bundled files only when needed.

For this project: the new path map is exactly a lightweight-identifier layer,
and the MCP `fetch_evidence` tool is the just-in-time handle. Two cheap
additions follow from the post: carry the modification time and a role line per
mapped file, and for large text files such as logs hand over head, tail and
matched-line counts rather than one window. The brief's order already follows
progressive disclosure (request, drafted prompt, exact excerpts, map, receipt).

Candidate C1: map entries with size, mtime and first line; a bounded
head/tail/count summary for any matched file above a size threshold, stored as
scan facts beside the exact excerpts, never in place of them.

Sources: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents);
[Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills).

### 2. Context rot: distractors cost more than length

Chroma's July 2025 report tested 18 models and found performance falls with
input length on simple tasks, a single semantically similar distractor lowers
accuracy and four compound it, low question-to-answer similarity degrades
faster, and, counterintuitively, shuffled haystacks beat coherent ones.

For this project: the brief is short, so length is not the risk; distractors
are. The collector's known weakness of selecting an unrelated utility file when
request terms are broad (`support/catalog/utility_002.py` in the log case) and
the twelve utility files the map listed there are distractors in Chroma's
sense. Precision in the brief matters more than one more excerpt.

Candidate C2: a distractor control in primary selection and the map: drop
candidates whose only matches are single common terms when higher-scoring
files exist, and report the drop as a cutoff. Measurable now with the Task Lab
span coverage and the decisive-file counts, no model required.

Source: [Context Rot: How increasing input tokens impacts LLM performance](https://www.trychroma.com/research/context-rot).

### 3. Token reduction is not cost reduction

Weinberger and Hozez (arXiv 2607.12161) ran paired, provider-billed Claude
Code tasks: the most aggressive tool-output reduction cut delivered tool-output
tokens by 38.4% and raised billed cost by 6.8%; prompt-cache traffic was most
of the input-side cost; and compression broke verbatim edit anchors, dropping
patch application from 27/40 to 15/40 in a small Go study. They recommend
success-adjusted billed cost per task. A September 2026 gateway study (arXiv
2609.22114) and a vendor evaluation by Factory make the same argument from
different data, the latter calling compression ratio "the wrong metric
entirely" and proposing tokens per task.

For this project: this confirms two existing positions, exact excerpts rather
than summaries, and MET-01's refusal to convert prompt shrinkage into a savings
claim. It also sharpens the metric the next comparison should report.

Candidate C5: record cache writes and cache reads separately from uncached
input in the comparison runner, and report cost per successful task with the
provider's published cache multipliers as a disclosed estimate, not a bill.

Sources: [Token Reduction Is Not Cost Reduction](https://arxiv.org/abs/2607.12161);
[An Empirical Cost Attribution of Context-Compression Gateways](https://arxiv.org/pdf/2609.22114);
[Evaluating compression (Factory)](https://factory.com/news/evaluating-compression).

### 4. Prompt caching mechanics bound how the brief should be shaped

OpenAI caches prompts of at least 1,024 tokens on an identical prefix and keeps
them for at least 30 minutes; GPT-5.6 and later bill cache writes whether or
not the prefix is reused. Anthropic caches tools, then system, then messages up
to a breakpoint, with a 5-minute default lifetime refreshed on use, a 1-hour
option at 2x write price, and reads at 0.1x.

For this project: within one host session the brief is a fixed user message,
so it caches once and is re-read each turn; the cost lever is turns, not brief
bytes, as the counters showed. Across briefs nothing is shared, so volatile
fields (job id, timestamps) do no harm. One rule follows: never regenerate or
edit the pasted brief mid-session, and keep the fixed receiving-assistant text
byte-identical between versions when possible so a user's follow-up pastes hit
the same prefix.

No new candidate; this is guidance for `docs/assistant-handoff.md`.

Sources: [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching);
[Anthropic prompt caching](https://platform.claude.com/docs/build-with-claude/prompt-caching).

### 5. Tool definitions are a host cost the app cannot fix, but can avoid adding to

Anthropic's advanced tool use post gives about 72K tokens for fifty-plus MCP
tool definitions loaded up front and an 85% reduction with on-demand loading;
Claude Code switches to deferred loading when tool descriptions exceed 10% of
the context budget. A competing vendor reports much lower accuracy for the
search tool at thousands of tools, which is a vendor comparison.

For this project: the app's five MCP tools and 740 bytes of descriptions are
negligible. The guidance to users stands: run the host with no unrelated MCP
servers for a Shake & Bake session, or use the paste path, which carries no
tool schemas at all.

Sources: [Advanced tool use (Anthropic)](https://www.anthropic.com/engineering/advanced-tool-use);
[Stacklok comparison](https://stacklok.com/blog/stackloks-mcp-optimizer-vs-anthropics-tool-search-tool-a-head-to-head-comparison/).

### 6. Repository instruction files can make agents work harder, not better

Gloaguen et al. (ETH Zurich, arXiv 2602.11988, February 2026) tested Claude
Code, Codex and Qwen Code on real issues with no context file, an LLM-generated
`AGENTS.md`, and a developer-written one. LLM-generated files reduced task
success and raised inference cost by over 20%; developer-written files gave a
slight improvement; agents respected the instructions and explored more. A
later two-agent study (arXiv 2607.27250) reads the same data as no significant
correctness effect for Claude-family agents, so the direction is contested but
the cost effect is not.

For this project: this is the closest external evidence about the drafted
prompt. Its asks and approach are LLM-generated instructions that a host will
respect, which can widen exploration and add turns, the very cost the brief is
meant to remove. The host-note diagnostic already found notes added no
accuracy. The next paired comparison needs an arm that tests this directly.

Candidate C6: three arms on the next frozen cases: exact evidence plus map
only; the same plus the drafted prompt; native retrieval. Report turns before
the first supported answer and cost per successful task per arm. If the drafted
prompt adds turns without adding supported answers, the design should drop or
shorten it rather than tune it.

Sources: [Evaluating AGENTS.md](https://arxiv.org/html/2602.11988);
[Do Context Files Help Coding Agents?](https://www.alphaxiv.org/abs/2607.27250).

### 7. Localization research: lexical recall, then rerank

Agentless localizes hierarchically (files, then classes and functions, then
edit lines) and mixes model-based with classic information-retrieval ranking.
SWE-Tester reports BM25 reaching 87.7% recall at top-30 with 3.4% precision on
test-file localization, and that reranking BM25's top-30 with Qwen3-Embedding
raised recall at k=1 from 27.2% to 46.6%, with the 0.6B reranker close to the
8B model at k=16. SpIDER adds graph-aware dense retrieval over the same
benchmarks. Ollama serves `qwen3-embedding` (0.6b, 4b, 8b) through `/api/embed`
with batch input and L2-normalized vectors; reranker models are community
builds only.

For this project: this is the strongest lead. The collector's scoring is a raw
term count; a BM25-style score (document frequency and length normalization,
pure Python, deterministic) is a drop-in improvement for the recall stage. More
important, it gives the local model a job that is checkable mechanically: rank
candidate windows by embedding similarity to the request, under the same byte
and count bounds, instead of writing prose. The Task Lab's required-span
coverage and the decisive-file counts measure it without any cloud run, and a
0.6B embedding model fits the owner's PC with room to spare. This is a use of
the local model that supports the user at use time, which is its stated role.

Candidate C3: BM25-style scoring in `search.prepare` (no model, no
dependency), measured on Task Lab and the four comparison fixtures.

Candidate C4: an optional embedding rerank of the candidate windows via the
existing loopback Ollama transport, with the same refusal, identity and budget
rules as the worker, recorded in the receipt as a scan fact. Qualification
stays with the existing gates: a reserved cohort, no promotion from
development material.

Sources: [Agentless](https://arxiv.org/abs/2407.01489);
[SWE-Tester](https://arxiv.org/pdf/2601.13713);
[SpIDER](https://arxiv.org/html/2512.16956v2);
[Ollama embeddings](https://docs.ollama.com/capabilities/embeddings).

### 8. Repository maps: reference graphs and budgets

Aider's map extracts definition and reference tags with tree-sitter, ranks
files and symbols with PageRank personalized toward identifiers the user has
mentioned, fits the result to a token budget by binary search, and caches by
file modification time. The project's November 4 note already chose to study
it through an adapter; today's definition index is a regex approximation of
its tag step.

For this project: tree-sitter is a compiled dependency, so it belongs in an
optional adapter at most. Two pieces are dependency-free: Python's `ast` gives
exact definitions and references for Python files, with the regex as the
fallback for other languages; and a reference graph over the index already
built during the walk can rank the map and the definition candidates by
centrality personalized to the request's identifiers, in pure Python.

Candidate C7: `ast`-exact Python definitions behind the same index interface;
a personalized reference-count ranking for the map; an mtime-keyed cache of the
index for repeat jobs on the same root, with the cache invalidated by any
changed identity, matching the existing "fresh task after changes" rule.

Sources: [Aider repository map](https://aider.chat/docs/repomap.html);
[Repository map pattern](https://www.agentpatterns.ai/context-engineering/repository-map-pattern/).

### 9. Prompt injection: the labels are right, and there is an experiment to run

Microsoft's spotlighting paper (arXiv 2403.14720) reports three ways to mark
untrusted text, delimiting, datamarking (a marker interleaved through the
text) and encoding, that cut attack success from above 50% to below 2% on
GPT-family models with negligible task cost; a reimplementation notes it does
not hold against adaptive attackers. Google DeepMind's CaMeL (arXiv 2503.18813)
separates control flow from untrusted data with provenance tracking, at higher
token cost, and discusses the dual-model pattern where a quarantined model
without tools handles untrusted input.

For this project: the architecture already is the dual-model pattern. The
worker has no tools and no authority, the host is told every excerpt and the
draft are untrusted data, and today's "software-selected" labels are a
provenance mark in CaMeL's sense. The open weakness is the 8B worker following
an injected instruction inside its own draft, which two wording revisions did
not fix. Datamarking is a mechanism, not wording, and it can be applied to the
worker's copy of the source only, leaving the exact evidence the host receives
untouched.

Candidate C8: datamark the excerpt text in the worker's source message (for
example interleaving a marker in whitespace) and rerun the injection case with
`qwen3:8b` and `qwen3.5:4b`. A pass on the exposed case is development
evidence only; the receipts are retained either way.

Sources: [Defending Against Indirect Prompt Injection Attacks With Spotlighting](https://arxiv.org/abs/2403.14720);
[Defeating Prompt Injections by Design (CaMeL)](https://arxiv.org/abs/2503.18813).

### 10. External datasets for an unseen cohort the project did not author

JetBrains' Long Code Arena bug localization dataset pairs real GitHub issues
with the pull requests that fixed them, in Python, Java and Kotlin, with dev,
train and test splits and repositories fetched separately; CodeRAG-Bench and
SWE-bench Lite cover repository-level retrieval in Python. These cases were
authored by other people, which meets the project's rule that AI-authored cases
count as exposed, with one caveat: public datasets may be in the cloud models'
training data, so they qualify the collector's recall, not a cloud host's
answers.

For this project: this is the first way to measure the collector on hundreds
of real, unseen cases with no model and no cloud. File-level recall of the
changed files against primary excerpts, context excerpts and the map, at a
fixed byte budget, is a mechanical number the existing dataset loader can
report. It also gives candidates C2, C3, C4 and C7 a common yardstick.

Candidate C9: an external-dataset adapter under `benchmarks/` that reads a
locally downloaded split and reports recall at the excerpt and map levels,
keeping repositories and data outside the checkout and recording the dataset
version. Licenses and sizes need checking before any download.

Sources: [lca-bug-localization dataset](https://huggingface.co/datasets/JetBrains-Research/lca-bug-localization);
[Long Code Arena paper](https://arxiv.org/abs/2406.11612);
[CodeRAG-Bench](https://aclanthology.org/2025.findings-naacl.176).

## Ranked plan

Ordered by what can be measured first without a cloud run, then by expected
effect on host turns.

| Rank | Candidate | Needs a model | Measured by | Gate |
| --- | --- | --- | --- | --- |
| 1 | C3 BM25-style scoring | no | Task Lab spans, decisive files, C9 recall | development |
| 2 | C2 distractor control | no | same | development |
| 3 | C9 external recall adapter | no | file recall at fixed budget | development |
| 4 | C4 embedding rerank of candidate windows | local embedding | same, plus receipts | reserved cohort before promotion |
| 5 | C8 datamarked worker input | local chat model | injection case receipts | development |
| 6 | C7 `ast` definitions, graph ranking, mtime cache | no | same as 1 | development |
| 7 | C1 map metadata and head/tail summaries | no | brief size, host turns later | development |
| 8 | C5 and C6 cost metric and three-arm design | cloud host | turns and cost per successful task | frozen cases, person-authored |

Ranks 1 to 3 change nothing about the local model and can ship as ordinary
collector improvements with receipts. Rank 4 is the first use of the local
model that is checked mechanically rather than read by a person. Rank 5 is the
one experiment left for the 8B injection weakness. Rank 8 is the host
comparison every earlier rank is preparing for; it still needs the candidate
frozen and the cases authored by a person.

## What this research does not establish

- Any result for this project. Published figures come from other systems,
  models, benchmarks and billing setups.
- That BM25 scoring, reranking or datamarking improves this collector or this
  worker; each is a candidate with a named measurement.
- Dataset licenses, sizes or suitability; C9 starts with that check.
- The direction of the instruction-file effect for Claude-family agents, which
  two studies read differently; the cost increase is the agreed part.
